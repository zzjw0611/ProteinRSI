# ProteinRSI 执行契约重构计划

日期：2026-10-14。下述执行契约已实现；验收结果见文末。未启动正式GB1实验或发布研究中的W/M版本。

目标：保留 Task Loop 和 Meta Loop，收敛授权、数据输入、动作执行和错误恢复。LLM继续自主定义科学流程、写代码、调用可选工具和修改 W/M；基础执行规则使用稳定接口。首次验收仍用组合突变优化，不扩展新任务能力。

## 第三轮故障的补充修复

后续真实运行暴露两处缺口：模型展示的 research_state 被移到顶层，而 Python
仍接收原始 research_context.research_state；局部修复输入的 context_shape 又被
递归猜测成 TaskView，导致框架报 KeyError(-1)，尚未请求修复模型就退出。

本次统一状态字段路径；工具清单、操作清单和修复资料共用从 TaskView 生成的
execution_contract；只有阶段的显式 view 进行任务状态投影。B-repair 独立准备
输入，保留代码、错误及类型说明，继续共用提供方容量保护、审计和恢复机制。
框架/提供方修复失败单独记录，不覆盖原始程序错误。

验收复用原有最小测试：真实 JSONLLM 上下文层＋模拟 HTTP 接口＋真实沙箱，
覆盖带历史的局部修复及两轮任务闭环。另只读提取失败研究的原始修复输入，
验证 49 条观测、2 轮历史的资料完整到达模拟接口；这些检查没有调用真实
LLM 服务、重启旧研究或取得新的 GB1 实测标签。

## 目标架构

```text
Task Loop
目标与初始输入
  → Planner：提出科学计划和需要的操作
  → Executor：动作 → 工具/代码执行 → 结果 → 下一动作
  → 候选交付：任务契约校验
  → Experiment：按预授权提交/回放并保存反馈
  → Analyst：解释反馈，更新工作记忆
  → 下一轮

Meta Loop
Task/Meta轨迹
  → Improver：诊断可复用能力缺陷，提出 W/M 版本
  → 已冻结的 direct 或 validate 策略
  → MethodGovernance：记录、激活或保留旧版
  → 后续轮次使用明确的方法版本

两条循环共用
研究授权、资源绑定、动作执行、执行回执、数据scope、代码沙箱、工具网关
```

Planner/Executor/Analyst是功能职责；不增加独立的权限Agent、修复Agent或数据搬运Agent。图引擎只推进状态，授权和实验记录仍属于同一个Agent系统的执行模块。

## 第一批：真实输入与局部恢复

优先处理已经使GB1阻塞的具体问题。

### 1. 稳定Python执行输入

修改：`dataflow/protocol.py`、`dataflow/resources.py`、`research/code.py`、`research/code_worker.py`、`research/context_frame.py`。

- 沿用真实 TaskView 作为后台执行上下文；模型展示摘要/分页引用不能成为执行上下文的替代品。
- 给 research_python 增加显式的命名资源引用输入，如 `resource_refs={"panel": "resource:..."}`。执行侧检查引用身份、Schema、当前研究/分支/证据scope，再把完整对象注入 `inputs["panel"]`。
- 只解析明确声明的引用端口，不扫描并猜测任意字符串是否为资源引用；注入端口不允许同时提供同名模型literal。
- 候选集合、已揭示观测、排除集合以原始获授权对象进入沙箱；数据库与oracle对象不进入沙箱。
- context_frame仍提供当前目标、状态、最新反馈、工作记忆和资源说明；历史详情继续按需查询。模型不需要为后台程序把整张表分页搬回。
- 原有按字节/token的请求保护继续工作；已有对象透传通过引用/适配器完成，不要求LLM生成完整原对象。

交付：第18轮那类“取回409条排除序列，重新输出task_context和candidates”的中间Agent步骤失去必要性。已注册工具契约、绑定和prompt明确指向后台数据注入。

### 2. 把执行结果与科学结果分开

修改：`tools.py`、`dataflow/protocol.py`、`dataflow/responses.py`、`dataflow/schema.py`、`replay/broker.py`、`replay/worker.py`、`recovery.py`；共享结果结构放入第二批的 `execution.py`，先定义接口再迁入。

- 为工具配置结果解释器；research_python的status=failed表示程序没有成功产出结果，不能按普通完成步骤进入completed前缀。
- 执行成功且检查返回passed=false，仍保留真实执行结果，但不能接受相应候选；不能把低fitness或模型预测不好当成程序异常。
- 错误信息包含kind、可修复字段/位置、恢复方式及原调用引用。RPC保留可公开的结构化错误详情，不只传异常类型。
- 修复参数或现场代码时产生原逻辑步骤的新attempt，保留旧代码、旧错误、旧输出；不重写已完成的候选生成，也不要求重写整个Protocol。
- Provider失败继续使用已有审计、重试和暂停规则；明确越权不可通过重新命名或修改代码恢复；副作用完成情况未知时先核对。

示例分类：

| 结果 | 处理 |
| --- | --- |
| 查不到已测记录 | ok＋无匹配，fitness保持未知，继续任务 |
| Python语法、变量或已公布字段使用错误 | 把错误交给当前Executor，局部修复代码 |
| 模型工具参数不合法 | 修复可由模型填写的参数 |
| 后台引用丢失、scope不匹配、可信输入注入失败 | 报运行时/完整性问题，不让模型编造对象 |
| 科学配对检查不通过 | 修候选或重新选择科学计划，保留真实检查结果 |
| 提供方已确认未完成的临时失败 | 走已有provider恢复策略 |
| 实验提交完成情况未知 | 核对同一提交身份，不能直接再次执行 |

交付：一个代码错误不会自然膨胀成新的Agent节点和重复的检查链。

## 第二批：统一授权与Agent执行

### 3. 授权与方法选择分离

新增：`permissions.py`。修改：`runtime.py:Campaign.initialize`、`tools.py`、`replay/broker.py`、`research/methods.py`、`research/meta.py`、`governance.py`、`evaluation_fork.py`。

- 从用户声明的工具配置、外发配置、生成代码开关、方法目标权限形成冻结的研究授权对象，保存其版本/指纹。
- W.tool_names继续表达方法选用工具；其有效工具集合必须是研究授权集合的子集。可用工具目录与执行网关使用同一判断。
- Task、Improver、验证分支共用同一个授权实现，但使用各自真实的证据和artifactscope。不能把两组后续测量或私有分析混在一起。
- M可请求使用授权工具、修改W/M程序和提示词；不能修改研究授权、已有实验事实或本次冻结验收规则。
- 网络、实验和方法激活效果来自已注册执行器，新自定义Schema/操作名称不产生额外权限。
- 预授权范围内自动执行；不增加计算总次数预算，也不增加每轮人工确认。

交付：M把ESMC从方法工具选择中加入或移除，只改变方法行为；ESMC是否获授权由研究配置决定。

### 4. 共用Agent动作协议

新增：`execution.py`，保持小模块，包含执行上下文、结果/回执接口及共享Agent步骤循环。修改：`agents.py`、`dataflow/integration.py`、`dataflow/protocol.py`、`research/runner.py`、`research/contracts.py`。

- Agent步骤统一返回“请求工具”或“最终结果”；最终结果继续由该步骤的科学输出Schema校验。
- 普通agent:propose和自定义agent:*复用同一执行逻辑。自定义步骤可以请求授权工具，其实际权限受研究策略和步骤范围约束。
- Planner声明科学目的、依赖、输入引用和最终输出；Executor使用共享循环执行动作，并在当前步骤内处理可修复错误。
- 保留动态Protocol、科学中间Schema和现场Python能力。基础权限及测量写入规则由执行接口决定，不由模型定义Schema来改变。
- native研究主路径采用同一个协议执行器。legacy/fixed路径先保留兼容适配及历史读取，避免同时大规模改写科学执行、历史格式和恢复语义；在新路径验收后再删除重复实现。

交付：模型可以自主增加有科学用途的分析步骤，但无需为了取得原始输入或填输出字段另造执行机制。

## 第三批：提示词、轨迹和版本兼容

### 5. 提示词与职责对齐

修改：`prompts/protocol_planner.md`、`protocol_step.md`、`designer.md`、`feedback.md`、`meta.md`。

- Planner：根据目标和已揭示证据决定科学策略、工具用途与流程结构；能采用新计划，也能复用适用的模板。
- Executor：取得系统注入输入，选择授权动作，写代码，观察结果，局部修复并交付合格输出。
- Analyst：解释测量、区分证据类型、更新有限工作记忆；保存结论和未决问题，按需查询历史。
- Improver：从Task/Meta轨迹诊断可复用能力缺陷，修改W或M，必要时保留经过验证的程序、策略和经验。
- 对所有角色统一说明：未知测量保持未知；后台输入无需重输；程序出错可修复，但不能放松用户约束或越权。

不预设“先粗后细”等固定突变规律，不强制使用蛋白引擎、每步LLM复核或每轮M修改。

### 6. 轨迹能区分四种变化

修改：`storage.py`、`trajectory.py`、`trace_export.py`、`governance.py`。复用已有命名空间和TXT导出。

```text
第N轮 / 方法W版本 / 方法M版本
  科学计划：为什么做这批候选
  步骤与动作：参数、后台输入引用、实际工具、代码哈希
  执行attempt：错误 → 局部修复 → 成功结果
  当轮计划变化：修改了什么未执行后缀，为什么
  实验结果：候选身份、实测fitness、查询数
  方法变化：W/M提案 → direct/validate处理 → 激活版本
```

每次调用用稳定的逻辑身份记录attempt；参数/代码变化有独立指纹；工具实现、输入证据、授权和输出契约变化进入缓存身份。实验提交身份不能因下游计划变化而重新创建。

执行纠错、当轮科学适应和持久W/M发布分别统计。纠错方法经保留并证明降低后续失败率，可以成为能力改进；一次临时修复本身不是改进效果证据。

历史实验保留原有执行语义。新版本先启动独立小研究验收；不通过修改快照校验或默默替换旧源代码来恢复暂停实验。新授权/动作契约进入方法执行快照，后续切换沿用现有轮次边界和回退机制。

## GB1前后案例

当前已经出现的路径：

```text
提出候选
  → Python检查返回failed，但步骤结果被持久记录
  → Planner追加准备检查/修复检查步骤
  → 新步骤取回并重输候选和上下文
  → 再检查
  → 接口不一致又追加修复
```

目标路径示例，具体科学分组仍由LLM决定：

```text
Planner：围绕FWAA探索，交付24个新候选
  → Executor：选择直接突变编辑，或写Python生成程序
  → 执行侧：注入panel引用、已揭示数据、排除集合
  → Python失败：保存attempt 1，修代码，执行attempt 2
  → 候选交付：基础约束与身份检查；必要的科学分组检查
  → Experiment：按预授权提交24个新查询
  → Analyst：根据真实反馈更新记忆
  → Improver：按需提出可复用W/M修改
```

第二轮仍可能选不同的候选或工具。这是允许的科学探索；原始数据、权限、候选身份、查询扣款和恢复契约始终明确。

## 最小验收

在现有测试中覆盖四个重要行为，不新增大量角色或Schema镜像测试：

1. 显式资源绑定能把完整获授权对象注入Python；错误scope或未授权工具被拒绝。
2. 一次Python失败在原步骤内修复，失败attempt不成为有效完成输出，成功上游不重复执行。
3. 历史查询为空可以继续设计；代码错误与正常科学负结果的处理不同。
4. 续跑复用已确认结果、避免重复实验；不确定副作用保持可核对状态。

真实服务验收可另行新跑2轮、每轮24个候选的LLM实测回放，检查候选合法性、标签隔离、实际查询数、上下文读取、LLM输出大小和修复轨迹；允许模型不调用蛋白工具、不提出M修改。本次代码修改仅运行本地机制测试，未启动该正式回放，不预先承诺固定耗时或fitness提升。

执行顺序：第一批完成并验收局部恢复，再完成第二批的共享授权和Agent循环，最后对齐提示词、轨迹及新版本验收。总共只新增两个核心模块，其余尽量复用现有实现。

## 第一批的实现边界补充

**Executor与模型。** Executor是执行职责和运行逻辑，不要求增加一个独立Agent实例。当前JSONLLM的role用于提示词调用、缓存和审计，API请求使用客户端的model；切换A/B/C标签不会自动切换模型。第一批沿用当前已配置模型，局部代码修复使用专门的repair提示词和可审计角色，并补齐guarded broker的角色允许列表。修复只取代码、错误、输入契约和必要样例，完整历史仍留在后台。以后可给code_repair单独配置模型，但要检查第三方服务实际可用性、质量和耗时，模型身份进入方法快照和缓存键；这不成为第一批恢复链的前置条件。

**数据载体。** 项目实际资源ID为resource:<hash>。research_python通过JSON请求启动独立worker；完整context写入受控临时目录的revealed-context.json，由worker在沙箱中装载，不依赖模型上下文展示策略。worker以exec执行脚本，前置注入context、inputs、artifacts和write_artifact，不是让生成代码import一个能访问Controller的上下文模块。显式resource_refs在执行侧解析成真实对象后放入inputs；超过256KiB的inputs通过受控输入文件装载。用户代码可定义run(panel, observations)，再用result = run(inputs["panel"]["items"], context["observations"])调用。函数签名由科学程序自行决定，稳定的是输入对象和result输出契约。

**M的算法产物。** 现有MethodProgram已支持name、purpose、code、inputs，能够作为W或M版本的组成部分持久保存；执行代码同时保存为programs/<hash>.py。它不是向src/proteinrsi安装任意Python模块，也不会自动成为原生ToolGateway工具。当前W程序在Team.run进入研究执行前运行，输出进入workflow_program_outputs；M程序供Improver的后续调用使用。第一批继续使用此版本化沙箱程序机制。发布按用户冻结的direct/validate策略执行，不添加每份代码都需人工批准的要求。若后续需要按程序名主动调用，可把已发布的MethodProgram包装成沙箱工具，仍继承原授权及数据scope，不能自动注册为拥有网络、实验或任意文件权限的新原生插件。

依据：[原子操作与权限核对](ATOMIC_OPERATIONS_AND_LLM_AUTHORITY_REVIEW.md)。

## 本次落地与验收

实现集中在两个共享模块：`execution.py`负责工具调用、原步骤纠错和可恢复的Agent动作循环；`permissions.py`负责冻结授权与可用工具判断。数据注入仍由ResourceStore及现有Python沙箱完成；Protocol、受保护worker和原生工具网关复用这些接口。旧研究无新授权记录时保留旧白名单语义，固定/legacy执行路径保留兼容适配。
